# Техническая архитектура

[English version](architecture.md) · [Главный README](../README.ru.md) · [Описание модулей](modules.ru.md)

Этот документ объясняет, как независимые модули Shadowrocket превращаются в готовые профили и как автоматические проверки защищают этот процесс.

## Цели архитектуры

Проект поддерживает два одинаково важных сценария:

1. **Отдельные модули.** Пользователь может импортировать модуль в Shadowrocket и включать или отключать его одним нажатием.
2. **Готовые профили.** Пользователь, который не хочет собирать конфигурацию самостоятельно, может импортировать `minimal.conf`, `advanced.conf` или `full.conf`.

Поэтому модули намеренно самодостаточны. Один домен может присутствовать в нескольких модулях, если без него они не смогут работать независимо. Точные дубликаты удаляются только при создании готовых профилей.

## Структура репозитория

```text
shadowrocket/
├── base/       # Общие настройки General, Rule и Host
├── modules/    # Независимо устанавливаемые модули
├── builds/     # Сгенерированные готовые профили
├── catalog/    # Машиночитаемый каталог модулей
└── custom/     # Пример пользовательских правил
scripts/
├── ruleslib.py          # Общий парсер и модель данных
├── build-configs.sh     # Генератор профилей
├── validate-rules.py    # Проверка структуры и синтаксиса
├── lint-rules.py        # Поиск конфликтов и ошибок порядка
├── validate-configs.sh  # Общая точка запуска проверок
└── check-domains.py     # Необязательная проверка DNS
```

## Поток обработки

```text
base.conf + выбранные независимые модули
                    │
                    ▼
            build-configs.sh
                    │
                    ▼
        minimal / advanced / full
                    │
            ┌───────┴────────┐
            ▼                ▼
    validate-rules.py   lint-rules.py
            │                │
            └───────┬────────┘
                    ▼
            GitHub Actions CI
```

`base.conf` содержит настройки, общие для готовых профилей. Модули содержат только необходимые для своей функции секции и должны работать отдельно. Готовые сборки являются генерируемыми файлами: изменять нужно их исходники, а затем запускать генератор.

## Как собираются профили

`scripts/build-configs.sh`:

1. Определяет все пути относительно корня репозитория, поэтому запускается из любой папки.
2. Создаёт временную рабочую папку через `mktemp` и удаляет её при завершении.
3. Выбирает заданный список модулей для каждого профиля.
4. Извлекает содержимое `[General]`, `[Rule]`, `[Host]` и `[URL Rewrite]` с помощью `awk`.
5. Сохраняет комментарии об источниках и удаляет точные дубликаты правил в готовом профиле.
6. Добавляет ровно одно правило `FINAL` в конец секции `[Rule]`.
7. Записывает результат в `shadowrocket/builds/` либо в `BUILD_OUTPUT_DIR`, когда валидатор выполняет изолированную контрольную сборку.

Порядок правил важен: Shadowrocket проверяет их сверху вниз. Поэтому конкретное исключение должно располагаться раньше общего правила, которое иначе перехватит запрос.

## Парсер и валидатор

`scripts/ruleslib.py` — общий слой разбора файлов. `SourceLine` хранит путь и номер строки, `Config` представляет разобранный файл, а `Rule` — нормализованное правило маршрутизации. Оба инструмента проверки используют эту модель и одинаково интерпретируют конфигурацию.

`scripts/validate-rules.py` находит однозначные ошибки:

- отсутствие обязательных метаданных и секций;
- неизвестные или повторяющиеся секции;
- содержимое вне секций;
- неподдерживаемые типы правил и политики;
- некорректные домены, IPv4/IPv6 CIDR и число полей;
- ошибки регулярных выражений, адресов и кодов в URL Rewrite;
- присутствие `FINAL` в переиспользуемых исходниках;
- отсутствие единственного `FINAL` в конце готового профиля;
- расхождение сохранённых сборок с результатом новой изолированной сборки.

Все результаты валидатора имеют уровень `ERROR` и завершают команду с ошибкой.

## Семантический линтер

`scripts/lint-rules.py` анализирует корректные по синтаксису правила, взаимодействие которых может дать неожиданный результат:

- один селектор с разными политиками;
- точные дубликаты;
- домен, перекрытый более ранним `DOMAIN-SUFFIX`;
- конкретный суффикс, перекрытый более ранним общим суффиксом;
- опасные правила `DOMAIN-KEYWORD`;
- одинаковые или пересекающиеся IP-сети;
- пересечения и различия политик между модулями;
- правила после `FINAL`.

Уровни результатов:

- `ERROR` — однозначный конфликт, способный изменить маршрутизацию; проверка завершается с ошибкой;
- `WARNING` — подозрительное или слишком широкое правило, которое нужно проверить;
- `INFO` — допустимое намеренное поведение, которое полезно показать разработчику.

Например, `DOMAIN,api.example.com,DIRECT` может находиться перед `DOMAIN-SUFFIX,example.com,PROXY` как намеренное исключение. Обратный порядок сделает точное правило недостижимым, и линтер сообщит о перекрытии.

Одинаковые правила с одной политикой в разных модулях имеют уровень `INFO`: самостоятельная работа модулей — требование проекта, а не ошибка. Генератор удаляет такие точные дубликаты только в готовых сборках.

## Проверка DNS

`scripts/check-domains.py` собирает конкретные значения `DOMAIN` и `DOMAIN-SUFFIX` из модулей и параллельно проверяет их разрешение через DNS. В отчёт попадают активные имена, NXDOMAIN, тайм-ауты, ошибки DNS, канонические имена и полученные адреса. Результат можно сохранить в JSON.

Эта проверка отделена от обязательной валидации, потому что DNS зависит от внешней и нестабильной среды: результат может меняться из-за резолвера, сети, региона или временного сбоя. DNS-ответ помогает обслуживать список, но не доказывает блокировку сервиса или правильность политики маршрутизации.

## Непрерывная интеграция

При каждом push и pull request файл `.github/workflows/validate.yml` пересобирает профили, запускает валидатор и линтер, а затем выполняет:

```bash
git diff --exit-code
```

Последняя команда завершается с ошибкой, если готовые профили отличаются от сохранённых в репозитории. Так изменение исходных модулей нельзя объединить без обновления `minimal.conf`, `advanced.conf` и `full.conf`.

Проверка состояния доменов запускается отдельно, поскольку зависит от сети и не должна блокировать детерминированные проверки конфигурации.

## Безопасное внесение изменений

Чтобы добавить или изменить правила:

1. Редактируйте нужный независимый модуль в `shadowrocket/modules/` и сохраняйте его самостоятельную работоспособность.
2. Размещайте узкие исключения раньше общих доменных суффиксов или IP-диапазонов.
3. Не добавляйте `FINAL` в модуль или `base.conf`.
4. Если новый модуль должен входить в готовый профиль, добавьте его в соответствующий список в `build-configs.sh`.
5. Пересоберите и проверьте проект:

   ```bash
   ./scripts/build-configs.sh
   ./scripts/validate-configs.sh
   python3 -m unittest discover -s tests -p 'test_*.py' -v
   git diff --check
   ```

6. Просмотрите все предупреждения и информационные пересечения. Неожиданные проблемы исправьте, намеренные — задокументируйте.
7. Сохраняйте изменения исходников и пересобранных профилей в одном коммите.

Не редактируйте файлы в `shadowrocket/builds/` вручную: при следующем запуске генератор заменит эти изменения.
